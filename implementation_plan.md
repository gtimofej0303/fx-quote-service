| Этап | Что делаем | Как проверяем готовность |
| --- | --- | --- |
| 1. Контракты и документация | Переносим согласованный контракт в `docs`, создаём первоначальный `api/openapi.yaml`. Фиксируем числовые ID и опциональный `Idempotency-Key` | Все операции, состояния и ошибки описаны однозначно |
| 2. Каркас и Docker-окружение | Создаём Go-модуль, конфигурацию, логгер, минимальный HTTP-сервер, Dockerfile и Compose. Поднимаем PostgreSQL, добавляем запуск миграций и отдельную тестовую БД | Проект собирается; приложение и PostgreSQL запускаются в Docker; приложение подключается к БД |
| 3. Доменный слой | Описываем валютную пару, котировку, задание, состояния и доменные ошибки | Unit-тесты проверяют нормализацию, допустимые пары, курс и правила состояний |
| 4. Схема БД и репозиторий | Создаём миграции, ограничения и индексы. Реализуем создание задания, идемпотентность, чтение результатов, захват заданий и атомарное завершение | Интеграционные тесты с PostgreSQL проверяют хранение, конкурентные запросы, транзакции и срок владения |
| 5. Сервисный слой | Реализуем создание обновления, получение по ID, получение последней котировки и обработку задания через интерфейсы репозитория и провайдера | Unit-тесты проверяют сценарии, переходы состояний, ошибки и решения о повторных попытках |
| 6. Внешний провайдер | Реализуем клиент Frankfurter: запрос курса, разбор decimal, проверку ответа, таймауты и классификацию ошибок | Тесты с управляемым HTTP-сервером проверяют успешные ответы и сбои |
| 7. Фоновый воркер | Подключаем сервис обработки к пулу воркеров. Добавляем ожидание повторов, восстановление зависших заданий и остановку | Задания обрабатываются в фоне; перезапуск не теряет их; устаревший воркер не может сохранить результат |
| 8. HTTP-хендлеры | Реализуем три endpoint, DTO, единый формат ошибок, request ID, ограничения запросов и health endpoints | HTTP-тесты подтверждают соответствие контракту и отсутствие обращения к провайдеру из POST-хендлера |
| 9. Сборка полного приложения | Связываем слои, завершаем readiness и graceful shutdown, проверяем сквозное логирование | В Docker проходит путь POST → воркер → результат по ID → последняя котировка |
| 10. CI и итоговая документация | Настраиваем автоматические проверки, завершаем OpenAPI и README с командами запуска и тестирования | Из чистого клона воспроизводятся запуск и проверки; CI проходит на GitHub |
